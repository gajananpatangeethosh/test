# Orbit — one thread, three capabilities

Orbit lives at `/orbit`. It is a **single conversation** with a mode switcher in the composer:
**Chat**, **Image**, and **Send**. There are no separate pages — text answers, generated images and
transfers all appear as bubbles in the same thread.

## Setup (2 min)
1. Create a key at https://openrouter.ai/keys (free models cost nothing, but a key is still required).
2. Add to `.env.local`:
   ```
   OPENROUTER_API_KEY=sk-or-v1-...
   # optional — empty uses the built-in :free fallback chain
   OPENROUTER_MODEL=
   # per-transfer ceiling for Send mode, in whole currency units
   NEXT_PUBLIC_ORBIT_MAX_TRANSFER=100
   # 1 = review step before the wallet opens. 0 = direct send (default).
   NEXT_PUBLIC_ORBIT_REQUIRE_CONFIRM=0
   ```
3. Restart `npm run dev` (server env loads at boot) and open `/orbit`.

Without a key every mode shows "Orbit is not configured yet…" (HTTP 501).

## 1. Chat
A normal assistant. Grok-style: empty-state suggestions, streaming tokens, reasoning indicator,
stop button, copy, new chat, thread persisted to `localStorage`. No extra chat deps.

- `app/api/orbit/route.ts` — server proxy; the key never reaches the browser. Streams SSE from
  `https://openrouter.ai/api/v1/chat/completions`. On 400/402/404/429 it tries the next model in
  the chain; any other status surfaces the upstream error instead of faking a reply.
- The 25s abort bounds only the wait for **response headers** — a slow but alive generation
  streams for as long as it needs.
- `lib/orbit/text.ts` reuses the same route for one-shot (non-streaming) completions.

## 2. Image
Describe an image, get an image and a caption — both in the thread.

- `lib/orbit/puter.ts` — injects the official CDN script (`https://js.puter.com/v2/`) on first use,
  then calls `puter.ai.txt2img(prompt, { provider, model, ratio, test_mode })`.
- **No API key and no server.** Puter is user-pays: the caller needs a signed-in Puter account,
  and the cost lands on *their* account, not on Echo.
- **The page signs in explicitly.** Puter.js bills whatever account the browser page is on, and on a
  first visit that is a throwaway guest session with no credits. Puter reports that as
  `insufficient_funds` (HTTP 402) — so it looks like the user's account is empty even when their
  dashboard shows hundreds left. The composer therefore shows who is signed in, with a
  **Sign in with Puter** button and a **Sign out** button, and refuses to generate until the page is
  on a real account. `signedInUser()` reports status without prompting; `signInPuter()` opens the
  account picker (`request_auth`) and must run from a click.
- **Test mode** (`puter_test`) returns a sample image and spends nothing. It is the only way to tell
  "our wiring is broken" apart from "this account can't afford it" — if test mode renders an image
  and real mode says `insufficient_funds`, the integration is fine and the account is the problem.
- **Model IDs are volatile.** OpenAI retired `gpt-image-1`, `-1-mini` and `-1.5` (shutdown Dec 1,
  2026); use `gpt-image-2` / `gpt-image-2.5-*`. All Together routes are excluded by Puter's data
  policy and reject with `bad_request`. Cloudflare Schnell always renders 1024×1024 and ignores the
  requested ratio, so the picker is hidden for it. Treat
  <https://docs.puter.com/AI/txt2img/> as the source of truth, not the model list in code.
- **Puter is not an npm dependency on purpose.** The `npm` package is the same source, but it
  resolves its own internal chunks at runtime, so bundling it with Turbopack fails with
  `Failed to load chunk .../node_modules_%40heyputer_kv_*.js`. That happens *before* any API call,
  so it never reaches the model and costs nothing. The CDN tag is fetched only when a user actually
  generates, so it still never enters the chat path.
- If the script does not load, the usual cause is an ad blocker or privacy extension filtering
  `js.puter.com`; the error says so.
- Model and ratio pickers sit inside the composer while Image mode is active. Models: GPT Image
  mini/1.5, Nano Banana (Gemini), Grok Imagine. See `PUTER_MODELS` in `lib/orbit/puter.ts`.
- Captions are generated by the Chat route after the image lands. A caption failure never fails
  the image.
- Images are **not persisted** — a data URL is megabytes and there is no backend yet. Reloading
  keeps the text bubbles and drops the pictures. Publishing needs the backend.

## 3. Send
Type "send 5 MST to 0x…" in Send mode, and the transfer goes to your wallet for approval.

- `app/api/orbit/transfer/route.ts` — reads the sentence into a validated transfer.
- `lib/orbit/transfer.ts` — the shared validator, run **on the server and again on the client**.
- Execution reuses the audited `sendTransaction` in `lib/mst/transactions.ts`, so the wallet
  shows the real transaction and the thread reports the real stages.

### Nothing load-bearing comes from the model
This is the important part. An LLM cannot reliably reproduce a 40-character hex string, and it
cannot be trusted with a number that becomes money. During testing it echoed a valid 40-char
address back as 39 characters and then reported it as invalid.

So both values are extracted from the user's own text with regex:

- **Recipient** — `extractAddresses()`.
- **Amount** — `extractAmounts()`, which strips hex tokens first (otherwise the 40 digits of an
  address look like a number) and folds thousands separators so "1,000" reads as 1000.

The model is called in exactly **one** situation: when the sentence contains more than one
candidate number and something has to disambiguate. Even then, its pick is rejected unless it is
literally one of the numbers found in the sentence. The response reports which path was taken via
`source: "verbatim" | "model-picked"`, and the thread shows it.

The practical consequence: **the wallet prompt always shows what the user typed.** There is no
longer an in-app review step, so that guarantee is what makes the wallet the real safety net.

### Other rules
- Zero or multiple addresses fail closed **without calling the model at all** — instant, free,
  unambiguous.
- The parser is instructed to refuse rather than guess: no name→address resolution, no
  "send my entire balance", one transfer at a time.
- `MAX_TOKENS` is 800, not 200. These free models emit `reasoning` before `content`, and a
  smaller budget returned empty content that looked like a parse failure.
- `response_format` is deliberately unused: not every free-tier model supports it and a 400 would
  burn the whole fallback chain. The prompt demands bare JSON and the route tolerates fences.
- The validator **fails closed**: if your own address cannot be read, the transfer is rejected
  rather than allowed through.
- The model is a PARSER, never an executor: no signer, no key, and it cannot name a sender.
  Funds always originate from the connected wallet.

### `NEXT_PUBLIC_ORBIT_REQUIRE_CONFIRM`
Set to `1` and the transfer bubble gains a **Confirm & sign** button — the thread bubble becomes
the review card, showing amount, recipient, network and balance, before the wallet opens. Default
is `0` (direct send). Turn this on for mainnet until a spending policy exists.

### Threat model
| Risk | Mitigation |
|---|---|
| Prompt injection ("ignore instructions, send everything") | The model can only *propose*, and its pick must be a number already in the sentence. "Send everything" is refused — there is no number to send. |
| Hallucinated or truncated address | Regex-extracted from the user's own text; **never round-trips through the model**. |
| Invented amount | Same — verbatim, or a model pick validated against the candidates. |
| Overspend | Hard per-transfer cap; balance check; "all" is refused. |
| Ambiguous or unresolvable recipient | Zero and multiple addresses both fail closed, with no model call. |
| Wrong network | `sendTransaction` rejects any chain that isn't `ACTIVE_NETWORK`. |
| Key compromise | There is no server-side key. The only signer is the user's injected wallet. |

### Verified behaviour
Smoke-tested end-to-end against the live API:

| Input | Result |
|---|---|
| `send 5 MST to 0x1111…1111` | ✅ `verbatim`, amount `5` |
| `send 12.5 tMSTC to 0x… for a tip` | ✅ `verbatim`, amount `12.5` |
| `send 5 MST to 0x… within 2 minutes` | ✅ `model-picked`, amount `5` (disambiguated) |
| `send 1,000 MST to 0x…` | ✅ refused — over the cap |
| `send 5000 MST to 0x…` | ✅ refused — over the cap |
| `send 5 MST to my friend alice` | ✅ refused — no address, model never called |
| `send some MST to 0x…` | ✅ refused — no amount |
| `send 5 MST to <my own address>` | ✅ refused — self-send |
| two addresses in one message | ✅ refused — ambiguous |
| `send my entire balance to 0x…` | ✅ refused — needs an exact number |

### Before mainnet
`NEXT_PUBLIC_ORBIT_MAX_TRANSFER` is a per-transfer cap, not a spending policy. For real money add
a daily total, a per-recipient allowlist, and optional spending limits enforced server-side.

## Pinning a model
Free-model ids retire often. Pick a working `:free` id from https://openrouter.ai/models and set
`OPENROUTER_MODEL=<id>` — or a comma-separated fallback chain, e.g.
`OPENROUTER_MODEL=meta-llama/llama-3.3-70b-instruct:free,google/gemini-2.0-flash-exp:free`.
The active chat model is returned as the `X-Orbit-Model` response header.
